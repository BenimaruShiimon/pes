# Руководство пользователя: верификация PoE watchdog в production

Это руководство предназначено для человека, который будет тестировать watchdog на реальном устройстве в production или в лаборатории перед развёртыванием в рабочей среде.

## 1. Цель

Проверить, что watchdog:
- корректно определяет "мертвое" PoE-устройство;
- вызывает power-cycle PoE-порта;
- после восстановления возвращает корректный режим PoE;
- не даёт ложных срабатываний на исправных устройствах.

## 2. Что именно мониторится

Watchdog проверяет состояние PoE-порта только по физическому интерфейсу:
- отсутствие `carrier` на `monitor_iface`;
- отсутствие трафика на этом интерфейсе через `idle_threshold`.

Проверка по сетевому адресу полностью отключена.

Решение о срабатывании задаётся параметром `watch_scope`:
- `os` — проверять только отсутствие трафика;
- `link` — проверять только отсутствие carrier/физического линка;
- `both` — срабатывать при любом из условий.

Дополнительно поддерживается `link_timeout_sec`: сколько секунд интерфейс может быть без `carrier`, прежде чем будет выполнен `power-cycle`.

## 3. Перед запуском

Проверить на целевой платформе следующее:

1. существует сокет `poed` либо PoE управляется через sysfs.
2. идентификатор порта совпадает с реальным аппаратным портом.
3. состояние интерфейса можно проверить на целевой платформе.
4. интерфейс мониторинга существует и является правильным uplink или port-facing интерфейсом.
5. `poe_ctl.sh` использует корректный метод для конкретной платы.

Полезные проверки:

```sh
ls -l /var/run/poed.sock
ls -l /sys/poe*
cat /sys/poe0/port_info
cat /sys/class/net/eth0/carrier
cat /proc/net/dev | grep eth0
```

Если устройство отдаёт PoE через sysfs, сначала вручную проверить путь до включения watchdog:

```sh
# числовой индекс
# пример для порта с индексом 0
echo 0 > /sys/poe0/port_power_off
echo 0 > /sys/poe0/port_power_on

# или по имени
# пример для порта G24
echo G24 > /sys/poe0/port_power_off
echo G24 > /sys/poe0/port_power_on
```

Добавить или обновить target из CLI:

```sh
/usr/sbin/poe_watchdog -A 'G01 5 3 60 5 eth0 30 SEMIAUTO link 20'
/usr/sbin/poe_watchdog -c /etc/poe_watchdog.conf -A 'G05 10 3 120 5 eth0 60 SEMIAUTO both 30'
```

Команда принимает формат без адреса, обновляет target по идентификатору порта и сохраняет строку в конфиг в физическом виде.

## 4. Подготовка конфигурации

Отредактировать `/etc/poe_watchdog.conf` и выбрать безопасную тестовую строку.

Пример для одного тестового порта:

```text
1    5    3    60    5    eth0    30    SEMIAUTO    link    20
```

Значение полей:
- port: `1`
- interval: `5s`
- fail threshold: `3`
- cooldown: `60s`
- cycle pause: `5s`
- monitor iface: `eth0`
- idle threshold: `30s`
- mode после сброса: `SEMIAUTO`
- watch_scope: `link`
- link_timeout: `20s`

Для более осторожного первого запуска лучше использовать `watch_scope=link`. Если всё стабильно, затем можно перевести на `both`.

## 5. Безопасная процедура тестирования

### 5.1 Первичный запуск

Запустить watchdog:

```sh
service S99poe_watchdog start
```

Проверить логи:

```sh
dmesg | tail -50
logread | tail -50
```

Искать строки вида:
- watchdog startup
- config parsed successfully
- carrier status
- packet idle status
- port power cycle triggered

### 5.2 Проверка здорового состояния

До искусственного сбоя убедиться, что целевое устройство доступно и работает.

Проверить:

```sh
cat /sys/class/net/eth0/carrier
cat /proc/net/dev | grep eth0
```

Во время здорового состояния watchdog не должен срабатывать.

## 6. Тестовые сценарии

### Сценарий A: потеря carrier на физическом интерфейсе

Цель: подтвердить, что watchdog реагирует на исчезновение живого линка на PoE-порту.

Как симулировать:
- отключить кабель или port-facing интерфейс;
- или принудительно снять `carrier` на `monitor_iface`;
- или временно обесточить порт/линк на уровне среды.

Ожидаемый результат:
- watchdog пишет в лог о потере carrier;
- после `link_timeout_sec` выполняет power-cycle;
- после `cycle_pause_sec` порт включается снова;
- `carrier` восстанавливается и watchdog выходит из сбоя.

Проверка:

```sh
logread | tail -100
cat /sys/class/net/eth0/carrier
```

### Сценарий B: только отсутствие трафика

Цель: проверить логику `os` / `both` без сетевых метрик.

Как симулировать:
- оставить устройство включённым и подключённым, но остановить генерацию трафика;
- или изолировать порт от потока пакетов, не отключая саму нагрузку.

Настроить конфиг:

```text
... eth0 30 SEMIAUTO os
```

Ожидаемый результат:
- счётчики пакетов перестают расти;
- после `idle_threshold` watchdog выполняет power-cycle;
- после восстановления порт возвращается в нормальное состояние.

### Сценарий C: защита от ложных срабатываний

Цель: убедиться, что watchdog не срабатывает на штатных всплесках трафика.

Как симулировать:
- оставить устройство живым и с нормально идущим трафиком;
- не блокировать carrier и не отключать поток.

Ожидаемый результат:
- no power-cycle;
- нет повторяющегося спама в логах.

## 7. Проверка восстановления после сброса

После power-cycle проверить:

1. порт снова включился;
2. PoE состояние восстановилось до заданного режима;
3. устройство снова появилось в сети;
4. watchdog перестал реагировать и вернулся в нормальный мониторинг.

Полезные команды:

```sh
/usr/sbin/poe_ctl.sh 1 status
/usr/sbin/poe_ctl.sh 1 on
cat /sys/class/net/eth0/carrier
logread | tail -100
```

Режим должен соответствовать заданному значению, например:

```text
SEMIAUTO
AUTO
OFF
```

## 8. Рекомендации для production rollout

Использовать по порядку:

1. Проверять на одном PoE-порту в лаборатории или на maintenance-сценарии.
2. Сначала запускать `watch_scope=link`.
3. Переходить на `both` только если поведение carrier и трафика стабильно.
4. Подбирать `link_timeout_sec` под реальную сеть.
5. Подбирать `idle_threshold`, чтобы не ловить ложные срабатывания на тихих устройствах.
6. Сохранять логи хотя бы на один цикл работы.

Рекомендуемые начальные значения:
- `interval_sec`: 5
- `fail_threshold`: 3
- `cooldown_sec`: 60
- `cycle_pause_sec`: 5
- `idle_threshold`: 30–120 в зависимости от типа устройства

## 9. Известные ограничения

- Некоторые устройства намеренно тихие и могут давать ложные срабатывания `os`, если выбран плохой `monitor_iface`.
- `watch_scope=both` жёстче и может быть слишком агрессивным для низкоскоростных устройств.
- На разных платформах могут быть разные имена sysfs-файлов и правила именования портов; проверять путь на конкретной плате.
- Нумерация портов может быть 0-based или 1-based; важно сопоставить её с реальной платформой.

## 10. Экстренные действия

Если watchdog ведёт себя некорректно:

```sh
service S99poe_watchdog stop
/usr/sbin/poe_ctl.sh 1 on
logread | tail -200
```

Далее:
- проверить конфиг на неправильный порт или режим;
- проверить корректное имя интерфейса;
- подтвердить, что тайминги и интерфейс мониторинга реалистичны;
- проверить, ожидает ли платформа числовой индекс или имя порта.

## 11. Чеклист перед запуском в production

Перед выкладкой проверить:

- [ ] watchdog запускается без ошибок;
- [ ] конфиг корректно парсится;
- [ ] восстановление после power-cycle работает;
- [ ] срабатывание по простоям интерфейса работает при включении;
- [ ] нет ложных срабатываний в обычном режиме работы;
- [ ] PoE режим восстанавливается после power-cycle;
- [ ] логи читаются и содержат достаточно деталей.

## 12. Итог

Этот watchdog рассчитан на низкий риск и локальную изоляцию: он не изменяет switch-app-логику, а работает как отдельный пакет PoE-мониторинга. Он особенно полезен для удалённых устройств, которые должны быть постоянно доступны и могут быть восстановлены автоматически, если перестают отвечать или перестают передавать трафик.
